The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), with project-specific grouping where useful.

## [Unreleased]

### Added

- **The server can present its own OAuth credential to a protected MCP source** (#254, stage 1): `oauth.clients` declares the credential this server presents upstream, beside the resource-server keys in the same `oauth` section, because one process serves both directions. Each entry selects one HTTP(S) MCP source with `namespace:<name>` or `url:<url>` (a trailing slash is ignored); a selector that names no source, several sources, a stdio source, or the same source as another entry — including when one entry uses `namespace:` and the other `url:` — fails the load, as do an unknown key, a relative `token_store`, an unset `client_secret_env`, and a source that already sets an `Authorization` header. `grant` is `client_credentials` (the default) or `authorization_code`, the latter a start/complete pair with PKCE whose verifier stays in the store and is never returned. Tokens live in SQLite at `$XDG_STATE_HOME/toolregistry/oauth-clients.db` or `~/.local/state/toolregistry/oauth-clients.db`, created `0600` with `0600` WAL sidecars inside a `0700` directory the server creates; the client secret is never written there, and the file permissions are the protection for tokens that must be replayed. A definitive rejection (a 4xx such as `invalid_grant` or `invalid_client`) clears the stored tokens and records the redacted reason, while a transient failure leaves the grant in place — a 3xx (redirects are never followed, so a token POST cannot replay the client secret to the host named in `Location`), a 429, a 5xx, a timeout, a transport error or a truncated response. A `client_credentials` rejection is retried on the next connect, because that grant has no interactive path; an `authorization_code` one stays latched until the operator authorizes again. An HTTP 401 or 403 from the MCP source on connect reaches the same handling: the stored access token is dropped and the rejection counted, so the next connect refreshes when a refresh token remains, refetches at once for `client_credentials`, or reports `reauth_required`; a second consecutive rejection latches an `authorization_code` source, and the counter resets only after a connect succeeds end to end. A token response without `expires_in` is assumed to last one hour from the row's `updated_at`, so an IdP that omits it causes one token request per hour per source rather than a token that never expires. A token endpoint taken from discovery that answers 404/410 is re-discovered once before the failure is classified. A source entry gains `reauth_required`, set by a definitive token-endpoint rejection and by an HTTP 401/403 from the MCP server itself. A stored token minted for another `issuer`, `client_id` or source URL is discarded, and a declaration that leaves the file takes its token row with it while a provider is running; a row left by a stopped process is reused only for the same selector, issuer, client and target, and must be cleared manually. Re-adding a source through the panel cannot reuse a credential whose declaration was removed. Metadata is accepted only when its `issuer` matches the configured one (or names an issuer, for a bare `discovery_url`) and its endpoints are absolute `http`/`https` URLs; a partial document is not cached. A definitive grant rejection stays latched until the operator re-authorizes or corrects the credentials in the file, while a 408, 425, 3xx, 429, 5xx, or a 404/410 on an explicit endpoint is transient. The stored credential fingerprint is PBKDF2-HMAC-SHA256 with a per-row salt, so the database alone does not permit a cheap offline recovery of the client secret. Not in this release: the panel authorize/re-authorize flow and its callback route, DCR/CIMD, a background refresh loop (a live connection keeps the header it connected with), outbound address screening for the configured OAuth endpoints, and a TTL on the cached authorization-server metadata.

- **The Sources page can edit a source, test it and show its tools** (#250): `GET /ext/gateway/sources/<id>` returns the status record with an editable declaration; `PUT` on the same path now merges the stored credentials and carries over the fields the form does not render (`tags`, `include`, `exclude`, plus `persistent` for MCP and `base_url` for OpenAPI), because the route replaces the whole declaration. `POST /ext/gateway/sources/test` tests the form's declaration and `POST /ext/gateway/sources/<id>/test` tests a stored one, without registering anything: MCP runs `initialize` + `tools/list` in a throwaway session and reports the tool count with the server name and version, OpenAPI fetches and parses the document and counts its operations, and a failure is returned verbatim with its exception type. `GET /ext/gateway/sources/<id>/tools` lists the tools a source registered with a short description and their enabled state. Secrets are write-only: no GET returns an MCP header, a Python `kwargs` value or an OpenAPI `auth.token`; the response names them under `secret_fields`, credentials in `url`/`base_url` are redacted and listed the same way, and a blank credential on save keeps the stored value unless `clear_secrets: true` is sent. The form's MCP credential is stored as the config file's header (`Authorization: Bearer …` or a named header). A connection test follows the declaration's own `allow_private_hosts`, the same policy registration applies.

- **The panel gains a Tools page with a guarded call tester** (#251): `GET /ext/gateway/tools` lists every registered tool including disabled ones, and `GET /ext/gateway/tools/<name>` returns the description, the served input schema, the output schema, tags, namespace, enabled state with its disable reason, source and redacted source detail, and the execution hints. `POST /ext/gateway/tools/<name>/call` runs the tool through the client execution path — the shared argument validator, the process permission policy, the route handler and the attributed log record under the operator principal — rather than a second one. The call needs `confirm: true`; a disabled tool is refused with `409` before it runs, invalid arguments answer `400` with the validator's detail, a policy refusal answers `403`, and a handler failure returns `ok: false` with the verbatim error while still being logged with its outcome. The route answers `401` without the panel's operator session.

- **The execution log can be filtered by principal, key, outcome, tool and time** (#252): `GET /ext/gateway/logs` and `GET /ext/gateway/logs/stats` share one filter set — `key_id` (with `operator` selecting the operator principal and never anonymous rows), `key_label`, `outcome` (`ok`, `error`, `busy`, `denied`, `timeout`, `disabled`), `tool_name`, `has_warnings`, `since`, `until` and `limit` — and the statistics are computed from the same filtered rows, so the counts always agree with the table. The outcome filter prefers the outcome recorded in `metadata` and falls back to the entry status, so `denied` and `busy` rows match when the backend recorded them. Each entry carries `principal: {key_id, label}`, where the label is the recorded client identity: a key label, an OAuth client id, `operator` for a tester call, or `anonymous` with no attribution. The view is served by the extension's own Logs tab, which supplements the core `/api/logs` page rather than replacing it, because the core handler lives in the installed `toolregistry` package.

- **The OpenAPI frontend serves Swagger UI's OAuth2 redirect page** (#245): `GET /oauth2-redirect.html` is served at the listener root by the standalone `openapi` server and under the mount path by the gateway, so a default gateway answers `/openapi/oauth2-redirect.html`. The page follows `--openapi-path`, is static and loads no external asset, and the `/docs` page now passes it the matching `oauth2RedirectUrl` — relative on the standalone server, prefixed with the mount path on the gateway, which also fixes the document URL under a mount. The route is unauthenticated by design: the authorization server redirects the browser without a bearer token, and the gateway answers the path before its bearer wrapper. The page mirrors the upstream `swagger-ui-dist` redirect script: it percent-decodes each callback parameter, accepts a hash callback with a leading `?` (`#?code=...`), and recognises the flow names `accessCode`, `authorizationCode` and `authorization_code`. Registering `<public origin><openapi path>/oauth2-redirect.html` at the AS is now enough to finish the authorization-code flow in the built-in Swagger UI.

- **OAuth tokens map to a full Principal** (#239): the `--oauth-scope` entry grammar is now `SCOPE=ENTRY[,ENTRY]`, where an entry is a namespace pattern, `+tool-name` to allow one tool or `-tool-name` to deny it; the namespace form is unchanged, and a deny wins when two granted scopes disagree. Scopes are read from `scope`, falling back to `scp` (string or array). The principal label is `sub`, else `client_id`/`azp`, else `oauth`, and the OAuth client is kept in a new `Principal.client_id` instead of being folded into the label, so two clients acting for one user have separate scopes, execution-log rows and counters (the accounting key is `oauth:<client_id>:<label>`). A client's in-flight limit comes from `--oauth-concurrency-claim` (default claim `max_concurrency`; a non-positive or non-integer value is ignored) or from a repeatable `--oauth-client-concurrency CLIENT=LIMIT`, and either only narrows `--client-concurrency`. The budget is held per OAuth client, keyed `oauth:<client_id>` and shared by every `sub` that client acts for, so a configured limit is not multiplied by the number of users; it is monotonically non-increasing, because a claim wider than the limit already in force does not raise it. Tool listing and call refusal behave like a scoped API key on both frontends, the execution log records `client_id` and `outcome` (`ok`/`error`/`busy`/`denied`), and configuring an issuer now enables the log by default, as a key store does. Refusals are recorded through a new `record_refused_call` with `ERROR` status, the precise outcome in metadata and empty arguments.

- **Optional RFC 7662 token introspection** (#253): `--oauth-introspection-url` turns on a confirmation call to the AS after local JWT verification, with `--oauth-introspection-client-id` / `--oauth-introspection-client-secret` sent as HTTP Basic. Only an `active: true` answer accepts the token; an endpoint failure rejects it unless `--oauth-introspection-optional` falls back to the local result. Answers are cached per token for `--oauth-introspection-cache-ttl` (default 5 s, `0` disables caching), which bounds how long a revoked token is still accepted; a failed probe is cached for the same TTL, so an outage costs one probe per TTL rather than one timed-out request per call. The cache is bounded and keyed by a SHA-256 digest, so the token itself is never stored, and neither the token nor the request body is logged. Opaque tokens remain unsupported because local JWT verification still runs first. The same settings can come from an `oauth` section in the configuration file (`introspection_url`, `introspection_client_id`, `introspection_client_secret`, `introspection_cache_ttl`, `introspection_optional`, `concurrency_claim` and `client_concurrency`); a command-line flag wins over the file, an unknown key in the section is a startup error, and a bad per-client limit names `oauth.client_concurrency[...]`. Leaving the URL unset keeps local verification only, which is the default.

- **Keys can be rotated and edited without changing their identity** (#248): `ApiKeyStore.rotate(key_id)` issues a new secret for an existing key and keeps the id, label, scopes, expiry, concurrency and usage history; the new digest and hash are written in one statement, so a concurrent verify sees the old pair or the new pair, and the old secret is refused on its next request. Rotating a revoked or expired key is refused. `ApiKeyStore.update(key_id, label=..., scopes=..., expires_at=..., max_concurrency=...)` changes the named fields only; a revoked key is refused, and an expiry in the past is refused as on `create`. `toolregistry-server keys rotate KEY_ID` and `keys update KEY_ID` expose both, with `--label`, `--namespace`, `--allow-tool`, `--deny-tool`, `--expires`/`--clear-expiry` and `--concurrency`/`--clear-concurrency`. The scope flags merge by category: `--namespace` replaces only the namespace list and the tool flags replace only the tool-override map, so a category without a flag keeps its value. Exit codes are `0` on success, `1` for an unknown key and `2` when the store refuses the change or `update` names no field. The Keys page gains a **Rotate** action, whose new secret is shown once with `Cache-Control: no-store`, and an **Edit** form for the same fields. `PATCH /ext/gateway/keys/<key_id>` and `POST /ext/gateway/keys/<key_id>/rotate` are the routes behind them.

- **Per-key usage is visible on the CLI and the Keys page** (#249): `ApiKeyStore` keeps one counter row per key in the `api_key_usage` table — `calls`, `ok`, `error`, `busy`, `denied` and `last_success_at` — incremented by one `INSERT ... ON CONFLICT` statement per call, so concurrent callers cannot lose an update. `keys list --usage` adds the object to every record, `keys get` always includes it, and `GET /ext/gateway/keys` and `GET /ext/gateway/keys/<key_id>` return it with each key. The Keys page shows Calls, OK, Errors, Busy, Denied and Last success as columns, and repeats every counter in the **Details** view. A refused call now counts too: an MCP `INVALID_PARAMS` denial, an OpenAPI `403` from the scope check, the proxy-target check or the process policy, and a call refused by the concurrency budget each increment `denied` or `busy`. The counters live in the key database rather than the execution log, so they survive a restart and stay visible after a key is revoked or expires; the log remains an in-memory ring of 1000 entries, so the two views agree only inside that window. A usage record never contains a secret, and a failed usage write never fails the tool call it was counting.

- **A resident hub can be started by a launcher**: `local-hub ensure` and the stdio shim spawn `TOOLREGISTRY_LOCAL_HUB_COMMAND` when it holds non-blank text, split like a shell command, instead of `toolregistry-server`. A Hub deployment points it at `toolregistry-hub`, so a hub started on demand keeps the Hub launcher's registry policy (preset defaults, configurable hook, admin panel). Unset or blank keeps the previous lookup: `toolregistry-server` on `PATH`, then the current interpreter with the package bootstrap. The spawned hub inherits the variable; only the shim's key is removed from its environment.

- **OAuth 2.0 resource-server foundation** (#234): `openapi`, `mcp` (HTTP transports), `gateway` and `local-hub` accept `--oauth-issuer`, `--oauth-audience`, `--oauth-jwks` and a repeatable `--oauth-scope SCOPE=NAMESPACE[,NAMESPACE]`. Bearer tokens minted by an external authorization server are verified locally against the issuer's JWKS (RS256/ES256 only, exact `iss`, `aud`/RFC 8707 `resource`, `exp`/`nbf` with 60 s leeway; the JWKS endpoint comes from `--oauth-jwks`, else RFC 8414/OIDC metadata, else `<issuer>/.well-known/jwks.json`, and is cached for 5 minutes; an unknown `kid` may force a refetch at most once per 30 seconds). The scope mapping is explicit and least privilege: an unmapped scope grants nothing. API keys and static tokens are tried first, then OAuth, so omitting `--oauth-issuer` leaves behaviour unchanged. MCP protected-resource metadata advertises the configured issuer in `authorization_servers`, a rejected request carries `WWW-Authenticate: Bearer resource_metadata="<metadata URL>"` on both the standalone server and the gateway (following the current MCP path), and a Unix-socket hub requires an explicit `--oauth-audience`. Token introspection (RFC 7662) is optional and off by default; see the #253 entry below. `PyJWT` with `crypto` is a new dependency of the `gateway` extra. Protected-resource metadata stops advertising `scopes_supported` once an external issuer is configured, because the authorization server may reject the generic `mcp` scope at authorize time: `--oauth-scopes "openid profile email offline_access"` names the scopes to publish, an empty value omits the field, and a server without OAuth keeps the previous `["mcp"]`. The configured issuer is compared verbatim for `iss`, so an authorization server that publishes a trailing slash is accepted; the slash is stripped only when composing metadata and JWKS URLs. RFC 8414 discovery tries the path-insertion form first for path-bearing issuers, then the suffix form, then OIDC. `local-hub` requires an audience whenever an issuer is set, even without `--socket`, because its ephemeral loopback bind is never a public audience. `pyjwt[crypto]>=2.10` joins the `openapi` extra, so OAuth works on the standalone command while the base install stays dependency-free.
- **The OpenAPI document describes the OAuth2 flow** (#235): when `--oauth-issuer` is set, the served document gains `components.securitySchemes.OAuth2` with an `authorizationCode` flow. `authorizationUrl` and `tokenUrl` come from the issuer's RFC 8414 or OIDC metadata and can be overridden with `--oauth-authorization-url` / `--oauth-token-url`; `--oauth-refresh-url` adds an optional `refreshUrl`. `scopes` is the `--oauth-scopes` list (empty is allowed). When API keys or static tokens are also accepted, the document-level `security` is `[{"OAuth2": []}, {"HTTPBearer": []}]`, meaning OR; an OAuth-only deployment lists OAuth2 alone, and a document without OAuth is unchanged. The scheme is omitted with a warning when the endpoints are unknown. The standalone server and both gateway OpenAPI assemblies share one builder. Static `--tokens` now stay accepted alongside OAuth even without a key store.

- **OAuth deployment and client documentation** (#240): new pages cover the resource server end to end — an [OAuth reference](reference/oauth.md) with every flag, its precedence and each command's derived audience; a [deployment guide](guides/oauth-deployment.md) for the discovery chain, reverse proxies, least-privilege scope mapping and troubleshooting; and [client walkthroughs](guides/oauth-clients.md) for Gemini custom connected apps (confidential client, Google-hosted redirect URI), Claude and ChatGPT connectors (CIMD, DCR or manual registration) and Swagger UI. The #234 and #235 entries are cross-referenced instead of repeated. The pages also recorded the gaps at that time — no introspection, no built-in authorization server, and no `oauth2-redirect.html` for the built-in Swagger UI page; the first and last are closed by #253 and #245 below.

- **The `oauth` configuration section carries every Track A setting** (#240): the section previously read only the introspection keys and the static client limits, so the issuer, audience, JWKS endpoint, OpenAPI flow endpoints and scope mapping needed flags. Every key is now named after its flag with the `oauth_` prefix removed (`issuer`, `audience`, `jwks`, `authorization_url`, `token_url`, `refresh_url`, `scope`, `scopes`, plus the existing `introspection_*` and `concurrency_claim`). `scope` takes a mapping from a scope to its entries, or the flag's `SCOPE=ENTRY[,ENTRY]` list; `scopes` takes a list of strings or a space-separated string. A flag still wins, and the file applies only when its flag is absent; the repeatable `--oauth-scope` flag's empty default falls through to the file, so a file `scope` cannot be overridden to nothing from the command line. A wrong type names its key as `oauth.<key>`, and `issuer` in the file alone turns OAuth on exactly as `--oauth-issuer` does. The issuer/audience gate now runs on the merged values, so a file-only `local-hub` deployment still needs an explicit audience, and the `openapi` reverse-proxy warning fires for a file-supplied issuer on a wildcard bind. The CLI reference gains the missing `--oauth-*` rows for `local-hub`, and the OAuth reference documents the full section and drops the corresponding gap.

- **The `oauth` section type-checks its values** (#240): `issuer`, `audience`, `jwks`, `authorization_url`, `token_url`, `refresh_url`, `scope`, `scopes` and the credential keys can now come from the configuration file, and every value is validated at startup. A quoted number (`introspection_cache_ttl: "5"`) is refused where it used to be converted with `float()`, a non-finite number (`introspection_cache_ttl: .nan`) is refused outright, and a number where a string is required (`introspection_client_secret: 9182736450`) is refused with a "quote a numeric secret" message — stringifying it would send the wrong credential, because the YAML parser rewrites `0123`, `0x1f` and `1_000`. The scope mapping is parsed by key and entries separately, so a scope name containing `=` (legal in RFC 6749) is granted as written. An error names the key as `oauth.<key>` and never echoes a credential's value.

### Fixed

- **A trailing-slash issuer no longer doubles the JWKS fallback slash** (#246): the last-resort fallback now uses the same composition as `OAuthSettings.jwks_url`, which strips a trailing slash, so an issuer published as `https://auth.example.com/` with unreachable metadata fetches `https://auth.example.com/.well-known/jwks.json` instead of `https://auth.example.com//.well-known/jwks.json`. `iss` is still compared verbatim.

## [0.9.0] - 2026-11-09

### Added

- **Every served call is recorded with its client identity** (#224): a deployment that sets `--keys-db` also enables the registry execution log, and each call that reaches a handler — MCP, and OpenAPI on both backends — writes one entry with its result or error plus `metadata={"key_id": ..., "client_id": ...}` naming the caller. A call refused by key scope, the proxy-target check or the process policy never reaches a handler and is not logged; an MCP refusal still writes an attributed structured-log line, while an OpenAPI refusal is not recorded server-side. `--execution-log` / `--no-execution-log` override the default on `gateway`, `mcp` and `openapi`. The log is an in-memory ring of 1000 entries per process, read by the admin Logs page, and follows core's redaction rules unless it was already enabled with `full_record`.

- Gateway admin frontend: `gateway` can host the core admin panel at a
  configurable path (`/admin` by default, disabled by default). The panel is
  reverse-proxied from a loopback `AdminServer` through the single public
  listener, uses the core panel's operator token/session instead of the
  gateway bearer tokens, and loads the gateway admin extension with the live
  key store, frontend registry and source manager. New options:
  `--admin`, `--admin-path`, `--admin-token`, `--admin-token-file` and
  `--admin-allow-private-hosts`. A missing operator token or an extension
  contract violation fails startup.
- **Runtime tool sources** (#185): `SourceManager` moves the Hub's hot-reload diff into the server. `add`, `remove`, `replace`, `retry` and `list` change the served tool set without a restart and keep a per-source `applied` / `excluded` / `failed` status with the redacted last error and a stable `src_<16 hex>` id (`to_dicts()` returns the JSON-ready list). API-originated mutations rewrite the config file after a `<path>.bak` copy and report `persisted` / `persist_error`; JSONC comments are not preserved, a read-only path is reported rather than silently ignored, and `--no-config-write` keeps changes in memory. The `--config-reload` watcher becomes a thin driver of the same manager and ignores the manager's own writes. Tools registered by a diff get the deployment profile applied, and a diff produces one route rebuild: `RouteTable.batch_changes()` collapses the per-event `refresh_all`, and `_rebuild` installs a freshly built mapping with one assignment instead of clearing the live one.
- **Gateway mode serves OpenAPI and MCP from one process** (#184): `toolregistry-server gateway` builds one ASGI application that mounts OpenAPI at `/openapi`, MCP streamable-HTTP at `/mcp` and MCP SSE at `/sse`, with configurable paths. Each frontend's enable flag is read per request, so a disabled frontend answers 404 without reaching the registry or rebuilding the MCP session manager; a path change applies on the next request. Bearer tokens from `--tokens` protect every frontend, and `/.well-known/oauth-protected-resource<mcp path>` is derived from the current MCP path. Frontend paths and flags live under `gateway.frontends` in the config file; `GatewayAdapter.update_frontend()` persists them after a `<path>.bak` copy and reports `persisted` / `warning`, while `--no-config-write` keeps changes in memory. Multiple frontends require the ASGI (`fastapi`) backend: `--backend httpserver` is rejected when a second frontend is enabled and can serve the openapi frontend only. One streamable-HTTP session manager is created at lifespan startup and closed on shutdown. `GatewayAdapter.list_frontends()` and `update_frontend()` are the in-process API for an admin extension.
- **A runnable gateway demo** (#188): `examples/gateway-demo/` serves `/openapi`, `/mcp` and a small `/ext/gateway` admin surface from one process, with client keys in a static JSON file (SHA-256 digests, shown once, revocable) and frontends that answer 404 while switched off. It uses `toolregistry-hub` tools when the package is importable and three local tools otherwise. A `Dockerfile` builds the image from the repository root, and `walkthrough.sh` re-runs the README steps against a live server in the `Gateway demo` CI workflow. The example lives outside `src`, so it is not part of the wheel or sdist.
- **Scoped inbound API keys** (#186): the optional `--keys-db PATH` flag on `openapi` and `mcp` opens a stdlib-SQLite key store. A key carries a label, a scope (namespace allow-list plus per-tool allow/deny overrides), optional expiry, revocation and `last_used_at`. The secret is printed only by `keys create` and stored as a per-key salted scrypt hash, so records, listings and database dumps never contain it. One principal resolver enforces the scope on all four surfaces — MCP `tools/list`, MCP `tools/call`, `/openapi.json` and the OpenAPI tool routes — by filtering the `RouteTable` view and refusing a call outside the key (`403` on OpenAPI, `INVALID_PARAMS` on MCP). The key row is read on every request, so revocation and expiry apply to the next request. `toolregistry-server keys create|list|get|revoke` is the headless wrapper over the same Python API (`ApiKeyStore`, `PrincipalResolver`) used by the admin extension; `list` is paginated and ordered by last use. Static `--tokens` credentials keep full, unscoped access and remain the bootstrap/legacy path; omitting `--keys-db` leaves behaviour unchanged, and the flag is ignored on the MCP `stdio` transport. When keys are enabled, `/tools` and `/openapi.json` carry a per-credential ETag plus `Cache-Control: private` and `Vary: Authorization`. Scoped keys keep the `discover_tools` / `call_deferred` proxy pair, and both enforce the key's scope (#195, below).
- **Scoped keys on the gateway frontends** (#200): `toolregistry-server gateway` accepts `--keys-db PATH`. One `PrincipalResolver` is built per process and passed to the OpenAPI app, the streamable-HTTP server and the SSE app, so MCP `tools/list`, MCP `tools/call`, the OpenAPI document and the OpenAPI tool routes enforce the key's scope on every frontend, including the httpserver backend. Static `--tokens` credentials keep full, unscoped access; the RFC 9728 metadata route is advertised when either credential source is configured; omitting `--keys-db` keeps the previous behaviour, and the key store is closed on gateway shutdown.
- **Scoped keys keep the discovery proxies, and both enforce the scope** (#195): `discover_tools` and `call_deferred` are no longer removed for a scoped key. Discovery results are filtered to names the key may call — on MCP, the FastAPI OpenAPI app and the httpserver backend — and `call_deferred` validates its `_target_tool` before dispatching, refusing an out-of-scope target with the same message a direct call to it gets. The target is resolved against the live registry (exact name, then the first registry-order normalised match), because that is what core invokes, so a tool registered while a configuration diff defers the route rebuild is judged too. The proxies stay visible whatever the key's namespaces are — they are registered in the default namespace and enforce the target's scope themselves — while an explicit per-tool override for either name still decides, so a key that denies them does not see them.

- **An OpenAPI source's document can be refreshed in place** (#182): `SourceManager.refresh(ref)` re-fetches a source's stored `spec_url` with its ETag and hands the document to core's `OpenAPIIntegration.refresh()`. A `304` changes nothing — no `last_refreshed_at` bump, no route rebuild. A changed document diffs added, removed and updated tools, keeps a hand-disabled tool disabled, and re-applies namespace tags, the deployment profile and `tool_metadata`; a tool whose spec regex cannot compile is dropped and reported in the diff. A moved `servers[0]` is adopted when the stored base URL came from the document, and only that candidate is checked against the outbound address policy. Every fetch re-validates the spec URL before I/O; a failure leaves the registry and the last good document in place. Exposed as `POST /ext/gateway/sources/<id>/refresh` and as a **Refresh spec** action on an OpenAPI source row. See [OpenAPI API](guides/openapi.md).

- **The httpserver OpenAPI app gains the remaining FastAPI surfaces** (epic #101): `/redoc` serves ReDoc from the CDN with a pinned release and an SRI hash, and the operator title is HTML-escaped like `/docs`. A tool registered after the app is built becomes callable without a restart through a `RouteTable` change listener that appends one POST route per tool; a removed tool keeps its route and answers 503, matching the FastAPI snapshot. Shutdown drains an in-flight request and removes the listener. The default backend is unchanged; retiring FastAPI is the next slice. See [Configuration](guides/configuration.md).

- **Route parameter overrides are applied from the configuration** (#165): a top-level `tool_parameters` block, keyed by the exact registered tool name, replaces the schema a route publishes and validates against without touching the registered tool. The server applies it where the route table is built, and again on every registry change: a config reload applies, changes or clears entries, a successful source `retry` applies the entry for the tool it brings back, and an OpenAPI refresh applies the entry for a tool it adds. Compatibility is judged against the tool's own model through the existing guard, so an override stricter than the model is logged and skipped, a looser one is applied with a warning, and an entry for an unregistered tool is logged and skipped; startup and reload never fail because of one entry. Clearing an entry drops the stored override even when the route is already gone, so a later tool with the same name does not inherit it. The block requires `toolregistry` 0.21.0 or newer. See [Configuration](guides/configuration.md).

- **The gateway can bind a Unix domain socket and publish a hub endpoint** (#145): `gateway --socket PATH` binds a Unix socket instead of a TCP address (POSIX only, takes precedence over `--host`/`--port`). Both backends validate the path before binding — an overlong `sun_path` (107 bytes on Linux, 103 on macOS), a non-socket file, and a live listener are refused, while a socket left by a crashed server is removed and the parent directory is created 0700. The uvicorn backend tightens the socket to 0600 right after startup, because uvicorn chmods it to 0666 itself. `toolregistry_server.gateway.endpoint` defines the document a resident hub will publish at `<state root>/hub/<name>.json` — name, protocol major, pid, version, transport and address, `started_at`, and frontend paths — replaced atomically, 0600 in a 0700 directory, and readable only when the file is owned by the caller, has no group or world bits, is not a symlink, and its writer is alive. The state root is `$TOOLREGISTRY_HOME`, else `$XDG_RUNTIME_DIR/toolregistry`, else `~/.local/state/toolregistry` (`%LOCALAPPDATA%\toolregistry` on Windows).

- **A resident local hub can be shared by local MCP clients** (#145): `toolregistry-server local-hub [run|ensure|stop|status]` serves the gateway as one process per machine, bound to `127.0.0.1` on an OS-assigned port (or `--socket PATH`) and named with `--name` (default `default`), so differently named hubs coexist. `run` serves in the foreground; `ensure` adopts a live hub or starts a detached one and prints its endpoint; `stop` signals the owner; `status` reports it and exits 0 or 3. Ownership is an exclusive lock on `hub/<name>.lock` that is never unlinked, with the owner pid in `hub/<name>.pid`, so a stale document cannot make `stop` signal an unrelated process: it requires the lock, the pid file and the endpoint pid to agree *and* the published address to accept a connection. Documents and logs are `0600` in a `0700` directory, the endpoint document is replaced atomically and carries a protocol major, and readers refuse a file that is not regular, is a symlink, has another owner, or is group/world readable. `--idle-timeout` (default 0, resident) exits after the given seconds without a request or an open MCP/SSE session. On SIGTERM the hub retires its endpoint and pid file before exiting. `local-hub` is POSIX-only for now; the actions refuse on Windows and point at `gateway`.

- **The shim keeps one stdio client usable across hub restarts** (#145): `toolregistry-server hub-shim` speaks MCP over stdio and forwards to the named hub over streamable HTTP. `initialize` is answered locally and `tools/list` is empty while the hub is down, so a client starts even when nothing is serving; a call then fails once with MCP error `-32000` and the shim reconnects in the background (0.25 s doubling to 5 s, one attempt capped by `--connect-timeout`, 5 s by default). After a reconnect the shim compares the hub's tool list with the one the client was last served — names, descriptions and input schemas — and sends `notifications/tools/list_changed` only when they differ. A document whose address accepts no connection is treated as "no hub", and the shim starts one through the `local-hub ensure` path unless `--no-spawn` is given; spawning needs `--config` and happens at most once a minute. A protocol-major mismatch is refused before serving. The transport and sessions are owned by one long-lived task, so a hub dying cannot cancel the stdio server, and Unix sockets are reached through the SDK's own HTTP client.

- **Clients on a shared hub are isolated per key** (#145, #223): headers that claim an identity, working directory or environment (`x-client-id`, `x-client-identity`, `x-client-cwd`, `x-client-env`, `x-client-environment`, `x-forwarded-user`, `x-remote-user`) are refused with `400` after authentication and logged with the caller's key, so identity can only come from the credential. Every call is counted per principal: `--client-concurrency` (default 8) caps in-flight calls, `--concurrency-timeout` (default 30 s) bounds the wait, a key's nullable `max_concurrency` — set with `keys create --concurrency`, changed with `keys set-concurrency` — can only narrow the process value, and a call that waits past the timeout returns MCP `-32000` "too many concurrent calls". Each call logs its `key_id` and `client_id`, and `/ext/gateway/clients` (the panel's Clients tab) reports live counters per client. `hub-shim` gains `--key-file` / `TOOLREGISTRY_HUB_KEY` and `--keys-db` for starting a key-scoped hub.

- **The standalone MCP server has the same per-client quota** (#223 follow-up): `mcp` accepts `--client-concurrency` (default 8) and `--concurrency-timeout` (default 30 s) on `sse` and `streamable-http`, with the same per-key narrowing and `-32000` busy error as the gateway. `stdio` validates both but runs unthrottled, because it serves one client with no per-client credential. The admin panel's Keys form also accepts `max_concurrency`, matching `keys create --concurrency`.

### Changed

- **The standalone OpenAPI server is zero-dependency, and FastAPI moved to a `gateway` extra** (epic #101): `toolregistry-server openapi` now runs only on the vendored `httpserver`, so `pip install toolregistry-server` serves the full OpenAPI contract with no third-party packages. The FastAPI assembly moved to the gateway-private `toolregistry_server.gateway.openapi_asgi`, used only by the gateway's ASGI backend; `create_openapi_app` and the ETag/body-limit middleware are no longer importable from `adapters.openapi`. `pyproject.toml` gains `gateway = [fastapi, uvicorn]` and keeps `openapi = []` as an empty alias; `all` pulls `[gateway]` plus `[mcp]`. **Breaking:** `--backend` and `--reload` are removed from the `openapi` command (both were uvicorn-only; the gateway keeps `--backend`), `OpenAPIAdapter(..., backend=...)` is gone, and `OpenAPIAdapter.app` now returns the vendored `httpserver.App` rather than an ASGI app. A gateway started without the extra raises an `ImportError` naming `toolregistry-server[gateway]`. See [OpenAPI API](guides/openapi.md) and [Installation](get-started/installation.md).

- **A key-scoped deployment accepts client keys only on MCP** (#145, #223): when `--keys-db` is configured, or in `local-hub` mode, an MCP request presenting a static operator token is refused for the whole path, `tools/list` included, because a shared credential cannot identify a client; `--allow-operator-token` (gateway, mcp and local-hub) re-admits it. OpenAPI and the admin panel keep accepting operator tokens. `local-hub` now requires `--keys-db`, and `hub-shim` needs a key file to reach a key-scoped hub.

### Fixed

- **`on_registered` now runs for startup sources** (#203): `SourceManager.apply_initial()` registered the config's sources but never called `on_registered`, so a downstream that relies on the hook for post-registration work — the Hub's `output_schema` pass — did nothing at startup and tools received that metadata only after a later diff. Startup now calls the hook once with every name the pass registered, before `tool_metadata` and the profile filter, matching a diff's order. It is skipped when nothing registered (an empty config or one whose sources are all excluded), and a raising hook is logged while the tools stay registered.
- **A same-name replacement is rechecked for an invalid spec regex, and partial drops are visible** (#171): the load-time check compared tool-name snapshots, so a source that replaced an existing tool with the same name contributed no *new* name and the replacement schema was never compiled — a bad `pattern` introduced by the replacement stayed registered and only failed on the first call. The check now compares tool objects: every name the registration created or replaced is inspected, and a replacement with an invalid pattern is dropped like a new tool. The source summary line now reports how many tools were dropped and which ones (for example `Loaded OpenAPI tools from '…': dropped 2 tool(s) with an invalid regex: ['a', 'b']`), and the all-dropped line carries the count and the list too. `--strict-spec-regex` and the hub's failed-source semantics (false only when nothing survives) are unchanged.
- **The httpserver backend reports the OpenAPI path it actually serves, and the comment-loss warning names both formats** (#196): the gateway reported the configured `/openapi` while that backend serves OpenAPI at the listener root (`/tools`, `/openapi.json`, `/docs`, `/events`). `list_frontends()` now returns `path: "/"` together with a `note` naming those routes, `update_frontend()` returns the same shape, and a submitted `"/"` is treated as "no change" so saving the unchanged record succeeds; any other path still gets the "cannot change at runtime" refusal. Persistence still writes the configured path, so the file reloads cleanly. `COMMENTS_WARNING` now says "comments are not preserved" instead of naming only JSONC, which was already inaccurate for the YAML writer.

- **The hosted panel keys its throttle on the real client** (#205): the gateway copied inbound headers to the loopback panel, so a client-supplied `X-Forwarded-For` reached it unchanged and every request appeared to come from 127.0.0.1. It now drops `Forwarded`, `X-Forwarded-For`, `X-Forwarded-Proto` and `X-Forwarded-Host` and states the socket peer, the scheme and the `Host` it saw. When the panel binds a loopback address the gateway also passes that address as a trusted proxy (`trusted_proxies`, core#431), so the panel's authentication throttle keys on the forwarded client: one client exhausting its bucket no longer locks out every panel user, and a forged header from an untrusted peer cannot rotate the key. A non-loopback bind trusts nobody, and the single-tenant assumption — a local process that can reach the panel port is a trusted peer — is documented next to the constant. The trusted-proxy wiring activates on `toolregistry` 0.21.0 and is a no-op on the 0.20.1 floor.
- **Saving an unchanged frontend no longer rewrites the config** (#209): the httpserver backend reports the openapi frontend at `path: "/"`, and the admin submits the record it displayed, so a no-op save mapped the path back to `None`, rewrote the file (dropping its comments) and reported `COMMENTS_WARNING`. The update now compares the record before and after and skips persistence when neither the path nor the flag changed, returning `persisted: false, warning: null`; a real change still persists and still reports the warning. The `path` docstring states that the reported `"/"` means "no path change".
- **The process permission policy was bypassed on the served frontends** (#145, #223): both the MCP and the OpenAPI call paths invoked the route handler directly, so a configured `PermissionPolicy` was never evaluated there — a rule that only the in-process API respected. Every call now resolves the policy through one helper on both backends, with `ASK` answered by the configured handler and otherwise resolved to the fallback (deny by default), and `call_deferred` is judged both as itself and as the tool it invokes. A registry without a policy is unchanged.
- **A key-scoped `tools/list` was empty on SDK v2** (#145, #223): the v2 list handler ran outside the request context, so the principal could not be resolved and the scoped route list came back empty while `tools/call` worked. The handler now publishes the request context before listing.
- **A policy that is not a `PermissionPolicy` was silently unenforced** (#223 follow-up): core's `set_permission_policy` accepts any object and its in-process path calls `evaluate`, while the server only enforced an instance of `PermissionPolicy`. A duck-typed policy is now logged once per type instead of being ignored without a trace; the type contract itself is Oaklight/ToolRegistry#467.
- **A shim-spawned hub inherited the client key** (#223 follow-up): `TOOLREGISTRY_HUB_KEY` was passed through to a hub the shim starts, so every process the hub spawned carried a credential it has no use for. The child environment now drops it.

## [0.8.0] - 2026-11-08

### Added

- **Spec-supplied regexes can run under a time bound** (#160): a new optional `regex` extra (not part of `all`) installs a `pattern_matcher` for request validation, so a proxied OpenAPI tool's `pattern` and `patternProperties` are enforced with 50 ms per match and a 250 ms per-request budget. `patternProperties` calls the matcher once per pattern (even for an empty object) and once per (pattern, key). A timeout answers `500` with `{"detail": "Tool '<name>' validation timed out"}`; a pattern that does not compile answers `500` with `"validation failed"`. Neither response echoes the pattern. Without the extra the behaviour is unchanged: spec regexes are not executed and `additionalProperties` stays relaxed at a level that carried patterns. Installing the extra tightens validation, so a payload that used to pass because its pattern was ignored can now be rejected. `--regex-timeout` / `--regex-budget` configure the bounds (`0` disables execution); `--strict-spec-regex` makes an invalid pattern abort startup instead of skipping that source.
- **Route-level overrides for served schemas and hints** (#137): `RouteTable.override_parameters(name, schema)` and `override_execution_hints(name, hints)` change what one route publishes without touching the registry `Tool` or its `schema_hash`. `RouteEntry` exposes the result as `served_parameters_schema` / `served_execution_hints`, and both adapters read that view, so MCP `inputSchema` / `annotations` and OpenAPI request schemas / `x-` extensions stay in step. `{}` suppresses every annotation/extension; `None` clears the override. Overrides survive `refresh()` and `refresh_all()` and notify listeners, so ETags and `tools/list_changed` reflect them. This replaces the need to wrap the private `tools/list` handler.
- **A zero-dependency HTTP backend for the OpenAPI adapter** (#127, #128, epic #101): `--backend httpserver` (or `OpenAPIAdapter(..., backend="httpserver")`) serves the same wire contract on the vendored `httpserver` — tool routes, `/tools` and `/openapi.json` with ETag/`304`, `/docs`, and `/events` over SSE — with no FastAPI or uvicorn installed. `fastapi` stays the default; `--reload` is reported as unsupported on the new backend. Results are serialised with core's `ToolResultJSONEncoder`, so dataclasses, pydantic models, sets, datetimes and nested containers keep the JSON shapes the FastAPI path produced; `bytes` stays base64 by design.
- **A differential parity suite between the two backends** (#129): both apps are served over sockets and the same request matrix is sent to each, asserting identical status, `ETag` and body bytes for tool calls, error envelopes, conditional GETs, 404/405, the disabled-tool 503 and the three auth cases.

### Changed

- **The core floor is now 0.20.1 and compatibility layers are removed** (#159, #154): `toolregistry>=0.20.1,<1.0.0`. `register_openapi_source()` passes `allow_local_files=True` directly instead of probing the loader signature, and the OpenAPI backends use core's `ToolResultJSONEncoder` directly: the non-finite fallback encoder and its capability probe are gone, so `NaN`, `Infinity` and a non-finite `Decimal` in a tool result are `null` on both backends. The minimum core version is enforced at install time; a core older than 0.20.1 is no longer supported. 0.20.1 is the patch baseline for this release: it carries the netpolicy special-purpose range fix (#425) and the discovery re-entrancy fix (#428), so 0.8.0 does not support 0.20.0.
- **A configured OpenAPI source now honours `allow_private_hosts`** (#176): the key was accepted by the config loader but `register_openapi_source()` never passed it on, so a spec or server URL on a loopback or private address was refused anyway. The flag now reaches both `load_openapi_spec()` (the spec fetch) and the `HttpClientConfig` the tools use; the client checks the base URL it actually uses (`servers[0]` or the configured `base_url`) before a request. It applies to that source only; unset or `false` keeps the default refusal.
- **A configured MCP source can reach a private address** (#168): `register_mcp_source()` dropped `MCPSource.allow_private_hosts`, so a config entry with `allow_private_hosts: true` still met core's outbound-address refusal. The server now forwards the flag with the registration call. It covers the HTTP, SSE and WebSocket transports of that source only; leaving it unset or `false` keeps the default refusal. That refusal names `allow_private_hosts` and never prints the resolved address, which stays on the exception's `addresses` attribute. Requires core 0.20.0 for the field, which the installed floor now enforces.
- **An invalid spec regex now drops only the affected tool** (#171): at load time the server compiles every `pattern` and `patternProperties` key in an OpenAPI source's tool schemas. Previously one invalid pattern removed every tool from the source; now only the tools whose own schema contains it are dropped, each with an error log naming the tool, the schema path and the pattern, and the source counts as failed only when no tool survives. `--strict-spec-regex` keeps the all-or-nothing behaviour and aborts startup. The load-time walker also no longer treats a property or definition *named* `default`, `example`, `enum` or `const` as a data keyword, so a schema such as `{"properties": {"default": {"pattern": "("}}}` is checked.
- **Only declared execution hints are published by default** (#136): a `READ_ONLY` / `DESTRUCTIVE` tag can be chosen for local permission policy, so publishing the resolved mapping turned that tag into a client-facing auto-approve claim. `served_execution_hints` now prefers `Tool.declared_execution_hints`; tag-derived values are published only when the `RouteTable` opts in with `emit_derived_execution_hints=True` or `set_emit_derived_execution_hints(True)`. Explicit hints are unchanged, and `MCP` / `OpenAPI` follow the same policy because both read the same view. On a core that predates `declared_execution_hints` the server reconstructs the same mapping from the `ToolMetadata` hint fields, which exist on the 0.19.x floor, so the default is safe without waiting for a core release; a core older than those fields publishes no claim.
- **Parameter overrides that tighten the tool's model are rejected** (core #384): `override_parameters` now refuses an override that adds `required`, tightens `minimum`/`maximum`/`minLength`/`maxLength`, changes `pattern`, narrows or changes `enum`, or narrows or changes a property's type on a model-backed tool, because the tool's validation model would not enforce the stricter contract. A looser override is saved with a `UserWarning`. Existing stricter overrides must be relaxed or moved to a proxy tool; proxy tools validate against the served schema and are unaffected. The rejection is raised by the programmatic `override_parameters` call. `toolregistry-server` itself applies no route parameter overrides from configuration, so upgrading cannot fail startup on its own; a downstream loader that does apply them should catch `ValueError`, log the tool name and reason, and skip that override so the service still starts.
- **OpenAPI requests are validated without pydantic models** (#123, epic #101): `_schema_to_pydantic`, `_resolve_type` and the `__annotations__` patching are gone. Bodies now go through `Tool.validate_parameters()` for signature-derived tools — the same coercion and unknown-key filtering `invoke` applies — and the vendored `jsonschema.schema_validate()` for proxy tools (MCP / OpenAPI / LangChain), which have no `parameters_model`. Both paths surface the existing 422 `{"detail": [...]}` envelope with `loc` / `msg` / `type`, so client-side error handling is unchanged. Bodies that are not JSON objects (arrays, strings, numbers, `null`, form posts) return 422 instead of failing in argument handling.
- **`/openapi.json` is produced by the `RouteTable` builder** (#124, epic #101): the document is built by `build_openapi_schema(route_table)` instead of FastAPI's `get_openapi()` over the generated pydantic models, so what the app publishes and what the standalone builder emits can no longer drift. Disabled routes are absent by construction.
- **Vendored jsonschema 0.4.4**: the bundled validator moved to zerodep 0.4.4; no public API change.

### Fixed

- **Request validation no longer blocks the httpserver event loop** (#161): `_validate_arguments` ran synchronously inside the async handler, so a large body or schema stalled SSE streams and every other request in the same process. Both OpenAPI backends now run it in a worker thread: the httpserver handler and the FastAPI async endpoint use `asyncio.to_thread`, while FastAPI sync endpoints already run in its thread pool. `HTTPException` still reaches the client as the same 422 envelope.
- **Tool failures in the OpenAPI backends log a traceback again** (#162): the vendored `structlog` chain has no `format_exc_info` processor, so `logger.exception()` reached `ConsoleRenderer` as `exc_info=True` and the traceback was dropped. Both backends now pass `exception=traceback.format_exc()` explicitly, the same way the MCP path does; the FastAPI adapter uses the vendored logger instead of stdlib `logging` so the keyword is accepted. The client-visible 500 body is unchanged.
- **Spec-supplied regexes are no longer executed during OpenAPI request validation** (core #384): a `pattern` or `patternProperties` from an OpenAPI document could backtrack catastrophically and hang a tool call, because Python's `re` has no timeout. Proxy tools are now validated against a copy without those keywords (`additionalProperties: false` is relaxed at the same level when `patternProperties` is dropped), while `/openapi.json`, the MCP `inputSchema` and the route ETag still publish the original constraints. Overrides keep their regexes; the upstream API remains the authority for field formats. In the same batch, `additionalProperties: {}` is no longer treated as `False`: an empty schema now permits extras, matching the override path, instead of accepting them in validation and then filtering them out.
- **A local OpenAPI path in operator configuration now loads** (core #376): core #376 made `load_openapi_spec()` reject local paths unless the caller opts in, and `register_openapi_source()` did not, so an `openapi` source pointing at a local file registered no tools and only logged a warning. The server now passes `allow_local_files=True`; the admin panel input remains http(s)-only.
- **The httpserver request-body cap is configurable** (#134): the vendored backend inherited a 1 MiB cap, so a tool call whose arguments exceeded that worked on the FastAPI backend and returned 413 on the httpserver backend. `--max-body-size BYTES` and `OpenAPIAdapter(max_body_size=...)` now set the cap; the default stays 1 MiB, a non-positive value raises `ValueError`, and an oversized body returns a JSON `413` with no traceback. A body large enough that the client is still writing when the server rejects it can still end in a connection reset — draining the unread body has to happen in the vendored server.
- **A core tool override now reaches every served schema**: `ToolRegistry.override()` swaps
  the `Tool`, and a `RouteEntry` holds a direct reference to it, but
  `RouteTable._on_registry_change()` ignored `ChangeEventType.OVERRIDE`.  MCP `tools/list`
  and the OpenAPI routes therefore kept the displaced description, title and annotations.
  `OVERRIDE` is handled like `METADATA_UPDATE`: the named route is rebuilt from the installed
  tool, including its description and `title`, and listeners are notified.  Listening clients
  receive `tools/list_changed`; the rest pick up the new definition on their next
  `tools/list`.  Pinned by
  `tests/test_route_table.py::TestRouteTable::test_override_replaces_the_route_and_notifies`
  (override, restore) and
  `tests/test_mcp_session.py::TestBackwardCompatibility::test_override_reaches_list_tools_title`
  (MCP `tools/list`).
- **Route overrides are validated and authoritative** (#138): an override is now a validated copy. `override_parameters` requires an object schema (accepting `["object", "null"]`), normalizes an omitted `additionalProperties` to `false`, fills `required` from the tool's validation model, warns when a model-required field is missing from the override, and rejects a typed `additionalProperties` that a model-backed tool cannot enforce. The OpenAPI adapter checks the served schema before the validation model, so a key the override omits is rejected with `extra_forbidden` instead of silently reaching the callable.
- **Non-finite tool results are strict JSON on both OpenAPI backends** (#130, #135): FastAPI serialised tool results through pydantic, which wrote a non-finite `Decimal` as the string `"NaN"`, while the httpserver wrote a bare `NaN`. Both backends now encode results with `adapters.openapi.serialisation.encode_tool_result()`, which emits `null` for a non-finite float or `Decimal`. The encoder is core's `ToolResultJSONEncoder`, so the projection is the same on the default matrix and on the `core-master` job (#159). Sharing one encoder also makes `bytes` results base64 on both backends (FastAPI previously decoded them as UTF-8), orders sets by `repr`, and sends `Content-Type: application/json; charset=utf-8` for tool results on both.
- **500 responses no longer echo the exception text** (#147, #150): both backends returned `str(exc)` as the execution-error detail, which can carry connection strings, internal paths and upstream URLs. Execution errors now return a stable message naming the tool, the full exception stays in the server log, and an unserialisable result gets the same treatment. The FastAPI backend now returns the same JSON `{"detail": ...}` envelope as the httpserver for an unexpected 500 instead of plain text.
- **MCP tool failures no longer leak the exception text** (#153): a tool exception was returned as the `isError` result payload with `str(e)`. The client now receives a stable `Tool '<name>' execution failed` message, and the full exception and traceback stay in the server log. Protocol-level errors such as `INVALID_PARAMS` are unchanged.

### Security

- **The OpenAPI backends harden credential checks and the docs page** (#149): bearer credentials are compared with `secrets.compare_digest` over SHA-256 digests in both the FastAPI dependency and the httpserver backend, and every configured token is compared so the position of a match does not leak. The operator-supplied `/docs` title is HTML-escaped, Swagger UI is pinned to 5.34.1, and both CDN assets carry an SRI hash. `/events` caps concurrent subscribers at 64 by default (`0` disables the endpoint; a negative value is rejected); extra connections get 503 instead of growing the queue set without bound.

### Added

- **A FastAPI-free OpenAPI document builder**: `toolregistry_server.adapters.openapi.spec.build_openapi_schema(route_table)` returns the OpenAPI 3.1 document straight from the `RouteTable`, emitting one `POST` per enabled route with the same `operationId`, `summary` (description truncated at 120 characters), namespace tag, inlined parameter schema, `x-*` execution-hint extensions and the `/tools` + `/events` meta operations as the FastAPI app publishes. When `discover_tools` is served, the response also carries `instructions` describing the two-step deferred-tool flow (`discover_tools`, then `call_deferred`), which a client could previously only infer from tool descriptions.

Legacy-era clients keep the existing session notification path; SDK builds without the listen hook are unaffected.

### Changed

- **Core floor is `toolregistry>=0.19.0` and the discovery/profile regression test is enforced** (#115): the server now requires the core line that invalidates the discovery index on disable events, so `apply_profile()` can no longer leave a disabled tool discoverable. The test no longer probes the installed core and skips on older releases; it runs unconditionally.
- **`tools/list` is cached for five minutes by default** (#114, **behavior change**): with `subscriptions/listen` served (#110), a listening client's cache is invalidated on every change, so `ttlMs` now defaults to the spec's example (`300000`) instead of `0`. A client that does not listen keeps the list for up to five minutes; `--tools-list-ttl-ms 0` restores refetch-every-time. `cacheScope` remains `private`.
- **`tools/list` cache hints are configurable** (#83): `--tools-list-ttl-ms` and `--tools-list-cache-scope` set the `ttlMs` / `cacheScope` hints on `tools/list` (SDK v2), which previously could only be passed as adapter kwargs and never were. The default stays `ttlMs: 0` ("never cache") until `notifications/tools/list_changed` is verified on SDK v2 (#107) — caching without a working invalidation would leave clients showing tools that no longer exist. `cacheScope` defaults to `private`, since the served set depends on profile and authorization.
- **Unknown or disabled tools are protocol errors** (#81, **behavior change** for MCP clients): `tools/call` for a tool that does not exist, or that is currently disabled, now returns JSON-RPC error `-32602` (Invalid params) instead of a `CallToolResult` with `isError: true`. The request itself was invalid, so hosts should not hand it back to the model as a tool result. Tool execution failures keep returning `isError: true` so the model can read the message and adapt. Works on both MCP SDK v1 and v2.

### Fixed

- **Dataclass tool results are serialized structurally** (#187, #192): `_serialize_result` used `json.dumps(..., default=str)`, so a tool returning `list[SearchResult]` reached the model as a JSON array of Python `repr` strings — not machine-readable, and un-indexable by field. Dataclasses (top-level or nested), datetimes, enums, paths, byte strings and sets now encode to their JSON equivalents; `str` remains only the last resort.
- **A `tools/call` resolves its route once** (#97): the route was looked up twice — once in the SDK v1 pre-dispatch hook, once in the handler. A disable landing between the lookups made the two SDK generations answer the same request differently: v1 an `isError` result, v2 a `-32602` protocol error. The hook's result is now carried to the handler.
- **Tool-list change notifications track the connection, not the request** (#108): on MCP SDK v2 every request gets a fresh `ServerSession`, so the session `list_tools` registered was garbage-collected before any change event could use it, and the tracker was always empty. It now records the underlying connection, which lives as long as the client. Delivery to modern-era connections still needs a back-channel (#107), so this is a prerequisite rather than a complete fix.
- **Only connections that can receive a change event are tracked** (#111): since #108 the `tools/list` handler tracks `session._connection`, but on the 2026-07-28 path that object is created per request and has no change-notification channel, so every `tools/list` added one dead entry that was never released. Tracking now skips modern-era connections (single-exchange HTTP and modern duplex alike); those clients are served by `subscriptions/listen` (#110). Handshake-era clients are still tracked.
- **A route change outside an event loop no longer leaves a coroutine behind** (#117): the notification scheduler built its coroutine before checking for a running loop, so building a server or mutating a route table from synchronous code emitted `RuntimeWarning: coroutine ... was never awaited`. The coroutine is now created only when there is a loop to run it.
- **`initialize` no longer advertises a disabled discovery stack** (#112, #113): the default `instructions` were attached whenever `discover_tools` existed in the route table, including when a profile had disabled it, so a client was told to call a tool that answers `-32602`. The guidance now requires both `discover_tools` and `call_deferred` to be enabled.
- **Source-level `include`/`exclude` filters are forwarded** (#88): the config loader parsed them, but `register_mcp_source()` and `register_openapi_source()` never passed them on, so a filtered remote source registered every tool. They are now forwarded unchanged (an explicit empty tuple still means "match nothing"). Takes effect once the installed `toolregistry` provides the fields; on an older core the server behaves as before.
- **MCP extra floor raised to `mcp>=1.22.0`** (#95): SDK releases below 1.22 import a pydantic internal that pydantic 2.12+ removed (`eval_type_backport`), so a resolver landing anywhere in 1.17–1.21 produced an install that fails at `import mcp.server.lowlevel`. 1.21 fails and 1.22 imports, so the floor is the boundary. The `test-mcp-v1` CI job now installs the declared floor and prints the version it tested.
- **Startup banner no longer corrupts the stdio stream** (#80): `print_banner()` wrote to stdout, which over the MCP stdio transport is the JSON-RPC channel — clients read banner art between their messages, sometimes after the first responses. The banner now goes to stderr, alongside the logs, and `print_banner()` accepts an optional `file` argument. `--no-banner` still suppresses it. The Hub calls the same helper, so it is fixed without a Hub change — but only once its installed `toolregistry-server` crosses the version that carries this.

### Security

- **Disable reasons no longer disclose the deployment profile** (#84): `apply_profile()` stored `Disabled by profile 'remote'` as the tool's disable reason, and that string reaches callers through the MCP `tools/call` error and core's `RuntimeError`. The stored reason is now the neutral `"not available on this server"`; the profile name is only logged server-side.
